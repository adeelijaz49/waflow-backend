## G. Security findings noticed during the audit (outside this build, but important)

1. `waflow-backend/.claude/settings.local.json` is **tracked in git and contains a literal Meta/WhatsApp Graph bearer token** — rotate the token and untrack the file.
2. `POST /send-message` (server.js) is unauthenticated and sends WhatsApp text/images from the platform number.
3. `POST /webhook` has no `X-Hub-Signature-256` verification; `GET /payment-cancelled?phone=` is unauthenticated and has side effects (clears carts, sends a WhatsApp message).
4. `cors()` is open to every origin; no `trust proxy` (so `req.ip` is the proxy address behind Azure); `mcp/oauth.js` interpolates request values into HTML unescaped; `AdminAuditLog.action` is a closed enum.
5. The 5 existing AI Mode chat tests, `orders.test.js` and 39 other test files delete rows and call real services — never run them against the shared database (the build's regression harness (kept outside the repository, see the Testing section of `README.md`) ran them on a throwaway DB with dummy credentials).

## H. Compliance-review follow-ups (2026-10-12)

The independent security review led to six compliance rules that are now enforced and tested inside the localisation code (the UTILITY floor, same-phone opt-out, template-level stop, referral-page privacy, inert test sends, log-before-mutate for staff flag changes — all described in `README.md`, "Compliance rules the code enforces"). What they leave open, or deliberately do not cover:

| # | Pri | Item |
|---|---|---|
| H1 | P1 | **The opt-out paths still opt out only ONE customer record.** The existing `STOP` / `optout_` branches of `server.js` and the Arabic hook resolve the customer with `Customer.findOne({ phone: from })`, so a second record of the same person (`+966...` next to `966...`, e.g. one added by the merchant and one auto-created by the Inbox) stays consented. The *localised* campaigns compensate (audience resolution and the sender exclude every recipient whose normalised phone matches ANY opted-out record of the workspace - one bulk read per audience, refreshed at most once a minute while sending), but the **existing English senders** (`sendPromotion`, loyalty reminders, bulk consent requests, carousels, Automated Flows) and the single consent ask (`consentAsk.js`) do not have that protection. Smallest change: make the STOP / `optout_` handlers (and `withdrawMarketingConsent`'s callers) opt out every record with that normalised phone (`find` + loop through `shared/consent.js`, which logs each `ConsentEvent` first) instead of the first match. `Customer.phone` has no index (only `workspaceId` does): add `(workspaceId, phone)` so the lookup is not a workspace scan on Cosmos DB. |
| H2 | P2 | **Compound index on `Customer (workspaceId, firstname, lastname, _id)` for Cosmos DB.** The deterministic name sort of the Arabic customer/language list (`customerLanguage.js`, `NAME_SORT`) needs it; without it Cosmos rejects the multi-field sort and the list falls back to the single-field `{ firstname: 1 }` sort the existing `/api/customers` list uses, i.e. a looser tie order between customers with the same first name (the page never fails). `models/Customer.js` is an existing file, hence a backlog item. |
| H3 | P2 | **`LocalizedSend` rows keep the recipient phone** (`phone` is required, denormalised exactly like `CampaignMessage` / `WhatsAppMessage` / `ConsentEvent`). Erasure parity: the existing internal-admin erasure tool anonymises only the `Customer` record (name, phone -> `deleted-<id>`, email, address, notes), so after an erasure the number survives on the send rows exactly as it already does on `CampaignMessage` and `WhatsAppMessage`. The campaign recipients view prefers the CURRENT customer record, so an erased customer shows as anonymised there, but the stored column keeps the number. If the lawyers want it gone everywhere, the erasure tool must also blank `phone` on `CampaignMessage`, `WhatsAppMessage`, `ConsentEvent` and `LocalizedSend` (`LocalizedSend.phone` is required, so write a placeholder such as `erased`, do not unset it). Campaign documents themselves hold only counts (plan samples are stripped). |
| H4 | P3 | **Customer-page language precedence is `?lang`, then the stored customer language, then `Accept-Language`** (then, for an Instagram link, the post caption's language before `Accept-Language`; for a referral link the referrer's language as a last resort). The original spec lists the stored customer language first; `?lang` goes first so the visible language switch on every Arabic page works for customers who have a stored language. Confirm with the owner; flipping it is a small change in `pages/index.js#decidePageLanguage` (an explicit `?lang=en` is already honoured before everything else). |
| H5 | P1 (legal) | **A typed Arabic yes/no counts as consent within 24 h of ANY consent ask** unless another pending flow (checkout confirmation / address) is waiting on that phone. "Pending" means the customer's `marketingConsentAskedAt` is less than 24 h old, they have not consented / opted out and no consent event has answered the ask since (`inboundHook.js`, `hasPendingConsentAsk`, `PENDING_WINDOW_MS`). The reply is **not tied to the ask message**: a typed reply normally carries no reference to it (only a swipe-reply carries `context.id`, which is not checked), so a "نعم" typed an hour after the ask - in answer to a different question - is recorded as the opt-in, source `... to pending consent ask (typed)`. The consent buttons (`consent_yes_<id>` / `consent_no_<id>`) are exact and unaffected, and a typed opt-out is always honoured. The owner's lawyer should confirm that a typed word is acceptable evidence of consent, or require the button tap (drop the typed opt-in / decline path in the hook). |
| H6 | P2 | **Frontend follow-ups for the new rules** (the Arabic area of the Angular app, `src/app/pages/localization` + `src/app/i18n/catalogs`): add the plan warning `category_floored {useCase}` (en/ar `campaigns.warning.category_floored`, plus `campaign-text.ts` known-codes list); show the campaign `lastError` `template_unusable:<Meta code>` as a readable "this template cannot be sent: fix or re-submit it" message (the report lists the `queued` remainder); in the template editor offer the UTILITY category only for the four transactional use cases (the server corrects it to MARKETING and returns the corrected value either way). Until then an unknown warning code renders generically and the raw `lastError` text is shown. |
