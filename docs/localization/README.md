# Arabic localisation for KSA (Phases 0–4)

Built 2026-10-11/12 from the owner's requirements PDF ("Arabic Localisation for KSA"). **Phase 5 (a fully right-to-left dashboard) is gated and was NOT built** — everything new is language-ready so it can follow.

Two stages, both behind the per-merchant flag (off for everybody until Waflow staff switch a merchant on):

1. **First build** (2026-10-11): *build it in separate files, don't touch existing code, don't break anything.* The feature lives in **new files** (sidecar collections, new routers, new services, a new lazy Angular area `/arabic`) plus a handful of additive hooks.
2. **Wiring phase** (2026-10-12, "finish the entire thing"): the existing senders, Automated Flows, bot replies, forms and screens now *use* Arabic for flagged merchants' Arabic customers, through small guarded, fail-open hunks that each call into a new module (complete list: "Existing-file edits"). English stays the default and is unchanged for merchants who don't enable Arabic, for English customers of flagged merchants and under the kill switch - with exactly the approved exceptions listed under "Approved global changes".

## Turning it on for a merchant

The feature is **off for everyone** until Waflow staff switch a merchant on (`LocaleSettings.arabicEnabled`, spec §8). Until then `/arabic` shows a "not switched on yet" card, the existing screens look exactly as before (one extra `GET /api/localization/settings`), and every `/api/localization/*` route except `/settings` answers `402 ARABIC_NOT_ENABLED`.

**Pilot rule: switch on the OLDEST workspace.** The production WhatsApp webhook is single-workspace (`server.js#resolveWebhookWorkspaceId()` = the oldest workspace by `createdAt`, one platform number for everybody), so customer replies, button taps, STOP, the shopping journey and delivery callbacks are all handled as that workspace. Arabic reaches real WhatsApp customers only for it. Another workspace can be flagged too (its dashboard sends carry its own `workspaceId` and its hub works), but its customers' replies cannot be matched by the webhook - an existing limitation (decision G5; there is no `phone_number_id` workspace resolution). Neither the admin page nor the CLI shows which workspace is the oldest; find it with this read-only command (run it where `MONGODB_URI` points at the target database):

```
node -e "const m=require('mongoose');require('dotenv').config();const W=require('./models/Workspace');m.connect(process.env.MONGODB_URI).then(async()=>{const w=await W.find().sort({createdAt:1}).limit(2).select('name createdAt').lean();console.log(w.map(x=>[String(x._id),x.name,x.createdAt.toISOString()].join(' | ')).join('\n'));await m.disconnect()})"
```

The first line is the workspace the webhook uses.

1. Staff page: `https://<backend>/internal-admin-localization` (HTTP Basic with `INTERNAL_ADMIN_USER` / `INTERNAL_ADMIN_PASSWORD` — **these must be set in Azure**; if they are not, use step 2).
2. CLI: `node scripts/localization-flag.js list | status <workspaceId> | enable <workspaceId> --notes "KSA pilot" | disable <workspaceId>` (uses `MONGODB_URI` from `.env`; writes `LocaleSettings` + `LocalizationAdminLog`; never deletes; `list` shows only workspaces that already have a localisation record).

A flag change reaches the webhook within ~30 s (flag snapshot), a customer-language or reviewed-name change within ~20-30 s (caches); other server instances can lag by the same amount.

**What a customer actually receives once a workspace is flagged.** Session text (journey replies, booking/order notices, referral text, pages, STOP/START answers) is Arabic immediately for customers whose language is Arabic - draft copy included (decision G1; `LOCALIZATION_ALLOW_DRAFT_PAGES=0` / `LOCALIZATION_ALLOW_DRAFT_SESSION=0` require reviewed copy instead). **Template messages** (promotions, loyalty reminders, consent asks, flow entry messages, the booking-confirmation fallback) stay English until the merchant has created the Arabic version in `/arabic/templates`, Meta has approved it **and** a native reader has marked it reviewed; the plan screens show how many customers get English instead and why (decision G4). Nothing is ever blocked and nothing falls back to English *after* an Arabic send was attempted (G3).

**Emergency switch:** `LOCALIZATION_DISABLED=1` turns every localisation behaviour off without a redeploy: English everywhere, new endpoints closed, B4 and the customer-language CSV column off. Still active under it (by design): the exact Arabic opt-out keywords (compliance) and the approved global changes H1, C3, B2/O4 (see below). Note that the typed-Arabic keyword hook (opt-out words, and opt-in words while a consent ask is pending) is **not** gated by the per-merchant flag - only the kill switch narrows it - so an Arabic "توقف" is honoured as an opt-out for every workspace, flagged or not; the flag gates language inference, the typed-yes/no rewrites for the existing flows and everything the wiring phase added. Rollback is therefore: flag off for the workspace (everything wired switches back to English within ~30 s), or the env var for everybody.

* **Sidecar collections** (no existing model changed except one optional field on `CampaignMessage`): `CustomerLanguage`, `LocaleSettings` (the flag + merchant defaults), `UserLocalePreference`, `LocalizedTemplate` (variants per language, each with Meta status + review status; `linkedMessageNodeId` or, since the wiring phase, `linkedPromotionId`), `LocalizedCampaign`, `LocalizedSend` (one row per recipient — unique per campaign/customer so a retry can never double-send), `ProductTranslation`, `LocalizationAdminLog`, and from the wiring phase `LocalizedFlowNode` (Arabic follow-up replies, unique per workspace/message node/language) and `LocalizedLegacySend` (one row per Arabic customer per run of an existing sender: sent / English fallback / skipped; English customers get no row). Nothing is ever deleted from any of them.
* **One WhatsApp door for new code**: everything the feature sends on its own goes through `shared/localization/transport.js` (`LOCALIZATION_SEND_MODE=dry_run` = nothing leaves the process). The existing senders keep using their own `waPost`; the wiring decides *which text/template* they send, never *how* it is posted.
* **Never silently wrong**: a customer only receives a variant that is Meta-APPROVED **and** (for Arabic/bilingual) marked *reviewed* by a native reader. If it isn't, the plan shows the fallback/blocked count *before* sending and the merchant must acknowledge it.
* **AI is advisory**: translate / Saudi-friendly / reply-in-Arabic return drafts with the AI notice; nothing is applied or sent automatically; AI text is saved as `draft`.
* **Consent is compliance-critical**: marketing only to opted-in customers (`canSendMarketing`, using the *effective* category - Meta's report **and the UTILITY floor**, see below); the opt-out button is in the message's language; Arabic opt-out keywords are honoured immediately (normalised: tashkeel/tatweel/alef variants/Arabic-Indic digits).
* **Fail open**: every hook/middleware that sits in an existing flow catches its own errors and falls through to the existing behaviour.

## Compliance rules the code enforces (each one is pinned by tests)

1. **The UTILITY floor (consent rule).** A merchant must not be able to bypass marketing consent by labelling a marketing message UTILITY. Only the *transactional* use cases `payment_reminder`, `booking_confirmation`, `booking_reminder` and `order_confirmation` can ever be UTILITY. For every other use case (`promotion`, `comeback`, `loyalty_reminder`, `points_balance`, `points_expiring`, `referral_invite`, `referral_reward`, `greeting`, `welcome_optin`, `custom`, and anything unknown) the **effective category is MARKETING** - for audience eligibility, planning *and* sending - whatever category was requested and whatever Meta reports (`variants[].metaCategory` is still stored as reported). The list lives once, in `shared/localization/category.js`; `campaignPlanner.effectiveCategory()` applies it, the sender re-evaluates it on the freshly read template before **every** recipient (a use case edited mid-run tightens the rest of the run), and templates create / update / library-copy store MARKETING for those use cases (corrected, never rejected - the returned template carries the stored value; a legacy row that still says UTILITY is validated, shown and submitted to Meta as MARKETING). A plan for a non-transactional template that is stored as UTILITY, or that Meta reports as UTILITY, carries the warning `category_floored {useCase}` (the floor acted). `welcome_optin` keeps its documented consent-request exemption: it needs the opt-in **and** decline buttons, never goes to opted-out customers and is not re-sent within 7 days (the exemption is decided by the use case and is never gained mid-run).
2. **Same-phone opt-out.** `Customer.phone` is not unique and the existing opt-out paths (the `STOP` / `optout_` branches of `server.js` and the Arabic inbound hook) update only the *first* customer whose stored phone equals the sender's number, so a second record of the same person (`+966...` next to `966...`) would keep receiving. In a campaign, a recipient is excluded - and counted under `skipped.optedOut`, stored as `skipped_opted_out` with `errorCode opted_out_same_phone` - when **any** customer record of the same workspace with the same *normalised* phone is opted out (any stored format matches: `966...`, `+966...`, `00966...`, spaced, Arabic-Indic digits). Resolved with **one bulk read per audience** (the workspace's opted-out phones), not one per recipient; the sender re-checks it for every recipient with that list refreshed at most once a minute. Deliberately simple: only an *opted-out* sibling excludes (a sibling that merely lacks consent does not). It applies to the localised campaign planner/sender (and `sendSingle`). **Since the wiring phase (H1, one of the three approved global changes - see "Webhook journey ..." below) the STOP paths also opt out every same-workspace record of the number, which protects the existing English senders too; this exclusion stays as the second line of defence.**
3. **A template-level Meta failure stops the campaign.** Meta errors `132000`, `132001`, `132012`, `132015`, `132016`, `132018` mean the template or its parameters are unusable for everybody. After **3 consecutive** such answers the run ends: no further Meta call, the recipients not reached stay `queued`, and the campaign is closed as `failed` (nothing was sent) or `partial` with `lastError = template_unusable:<code>`. Rate-limit codes keep their back-off; any other outcome (a success, a recipient-level failure) resets the streak; recipients skipped without a Meta call neither count nor reset it.
4. **Public referral pages show no personal data of the referrer.** The Arabic `/r/:code` and `/c/:code` interstitial used to say "{referrer's first name} invited you" to anyone holding the link. It now shows only the business context - the merchant's business name (`Settings.merchantName`, else the workspace name unless it is the auto-generated "<x>'s Workspace"), the promotion name and the merchant-written friend-reward text - and the referrer's customer record is never read for the page. The referrer's stored *language* is still used, never displayed, as a last-resort hint for the page language.
5. **Test sends are inert.** The opt-out button of a template test-send carries the payload `l10ntest_optout`. The old `optout_test` was a *real* opt-out of whoever tapped it (both the existing handler and the Arabic hook dispatch on the `optout_` prefix).
6. **Staff flag changes are logged first.** `/internal-admin-localization` (and the CLI `scripts/localization-flag.js`) write the `LocalizationAdminLog` row **before** changing the flag (log-before-mutate, like `shared/consent.js`); if the row cannot be written the flag is left untouched and the operator gets a "nothing was changed" page. If the flag change itself fails after its row was written, the page says so (the row records the *attempt*; check the workspace page for the real state before retrying).

## Existing senders (wiring phase, D1)

`shared/localization/legacySenders.js` is called from inside the existing per-customer loops of `ops.sendPromotion` (dashboard `POST /api/promotions/:id/send`, AI Mode `send_promotion`, MCP, GPT Actions), `ops.sendLoyaltyReminders`, `ops.sendConsentRequests` and the referral link send. The existing consent gate, demo handling, 300 ms pacing, `CampaignMessage` bookkeeping and return shapes are untouched; the seam only answers "does an Arabic send apply to THIS customer". It applies when ALL hold: kill switch off, the workspace is flagged, the customer's language is Arabic (customer -> merchant default -> English), the customer is consented and not opted out (also not via a same-phone sibling), the promotion is not a carousel (decision G8) or a demo send, and the merchant has an Arabic version that is Meta-**APPROVED + reviewed**, has the opt-out button (marketing) and whose button/field requirements are met.

* **Promotion:** a version linked to the promotion's custom entry message (`linkedMessageNodeId`, only when that English entry message is approved) or a version linked to the promotion (`LocalizedTemplate.linkedPromotionId`, button role `shop_now` = payload `promo_<promotionId>` so the shopping journey continues in Arabic). **Loyalty reminder:** the library use case `loyalty_reminder` / `loyalty_reminder_balance`. **Consent request:** `welcome_optin` (needs the opt-in and decline buttons; stamps `marketingConsentAskedAt` exactly like the English ask; never sent to opted-out customers).
* **Everything else is English exactly as today** (G4): no usable Arabic version, version pending / not reviewed / rejected, fields that cannot be filled, a customer without a language. The plan says so beforehand and the response says so afterwards.
* **After an Arabic attempt nothing falls back to English** (G3): a failed Arabic send is a failed row, not a second English message. Three consecutive template-level Meta errors (`132000/132001/132012/132015/132016/132018`) stop the remaining Arabic customers of that run (they get no message and a skipped sidecar row); rate-limit codes back off 5 s; every Arabic send has a 30 s timeout.
* **Plan and report (hub + the existing screens):** `POST /api/localization/promotions/:id/send-plan`, `POST /api/localization/senders/:sender/plan` (`loyalty_reminder`, `consent_request`), `GET /api/localization/promotions/:id/send-report` (per language sent / failed / skipped / delivered / read / clicked / ordered, fallbacks by reason, delivery failures by Meta code). The send responses gain `localization` / `languageCounts` **only** when an Arabic customer was in the batch. All 402 for unflagged workspaces.
* **Test sends:** the legacy `ops.sendTestMessage` and the AI Mode / MCP / GPT test sends stay English; Arabic tests use `POST /api/localization/promotions/:id/test-send` (inert opt-out payload, no `CampaignMessage`).
* **No per-send language override in the existing composer** (G7): default = each customer's own language; the Language panel has selection shortcuts (keep only Arabic / only English / skip the fallbacks) and a link to the hub campaign builder (`/arabic/campaigns/new`) for English-only / Arabic-only / bilingual sends.
* **Session-text notices** (booking confirmed / cancelled / rescheduled / declined, order summary + pay link, referral link text): `utilitySend.js` renders the catalogue text (`catalog/senders.json`, 17 drafts) for an Arabic customer; the consent-ask carrier of `sendUtilityMessageWithConsentAsk` is mirrored; when Meta answers 131047 (outside the 24-hour window) an approved + reviewed UTILITY `booking_confirmation` Arabic template is sent instead; item/service names are the merchant's **reviewed** Arabic names only (G2). The referral text carries an Arabic opt-out hint line (`senders.optOutHint`, needs the lawyer).
* **Not covered:** referral reward notices (no English sender exists - backlog A5), payment/booking *reminders* (no English sender exists either), carousel promotions, the fixed default flow messages (below), first-contact sends, merchant free text.

## Automated Flows (wiring phase, D2)

* **Entry message.** `utils/flowScheduler.js processEnrollment` calls `flowBridge.sendLocalizedFlowMessage` right after the atomic claim. An Arabic customer of a flagged workspace gets the Arabic version of the flow's entry message when the flow sends a **Promotion** (or a legacy custom entry message) that has an Arabic template linked to the entry node (`linkedMessageNodeId`), Meta-approved and reviewed, and the English entry node itself is approved. The Arabic `CampaignMessage` row carries `workspaceId` and the `msgnode_<id>_<position>` / `optout_` payloads. Any other case: the unchanged English send.
* **Follow-up replies** (what a customer gets after tapping a button; free session replies, no Meta approval). The Arabic text lives in the sidecar `LocalizedFlowNode` (per message node, one row per language, `contentVersion`, hash of the English text it was written against). It is sent only when **reviewed, free of issues and not stale**: editing the English reply makes the Arabic one stale (customers get English until it is re-saved and re-reviewed). Entry templates have **no** such staleness gate - they are Meta-approved text and keep sending until the merchant changes them. The follow-up language follows the **customer's** language; there are no bilingual follow-ups. A failed Arabic follow-up is a failed row, never an English resend.
* **Hub:** `/arabic/flows` shows every flow with its whole message tree and, below them, the promotions that have a custom entry message but are not used by any flow, per-node per-language status, an English / Arabic / Both preview and an editor for follow-ups (AI translate / Saudi-friendly give drafts the merchant must apply and save), with deep links from the existing Promotions and Flows screens (`?node=<messageNodeId>`). API: `GET /api/localization/flows/tree`, `GET /api/localization/flows/promotion-trees` (promotion-owned trees no flow uses, at most 200), `/owners/:flow|promotion/:id/tree`, `/followups/:nodeId`, `PUT /followups/:nodeId/variants/ar`, `POST /followups/:nodeId/variants/ar/review` (409 `CONFLICT` / `STALE_SOURCE` on a stale review).
* **Not covered (G9):** the fixed default flow templates (win-back, post-purchase, points nudge, no-show) have no Arabic overlay - the hub tells merchants to attach a Promotion to the flow and add Arabic to that promotion. The price slot of an Arabic flow entry message is filled by the existing English formatter (for example "45.00 SAR", not "45.00 ر.س").
* **Existing defect, not changed (IB-13, G6):** the English flow engine writes `FlowEnrollment` / `CampaignMessage` rows **without `workspaceId`** and its trigger queries are not workspace-scoped. See "Known limits" below.

## Data, forms and pages (wiring phase, D4)

* **B2 (global):** see "Approved global changes". **Customer language:** the sidecar `CustomerLanguage` stays the store (the Customer model is unchanged); the existing profile shows/edits it through `GET|PUT /api/localization/customers/:id/language`; the customers CSV wizard maps a `language` column (`ar`, `en`, `Arabic`, `English`, Arabic words) for flagged workspaces: an invalid cell is a row error, blank/unknown never clears a stored language, a CSV never overrides a language the customer chose (`customer_chose`), and a re-import of existing customers updates the language.
* **Arabic names:** products and services get an optional Arabic name/description (existing forms, the hub catalog tab, and optional CSV columns such as `name_ar` / `description_ar` or their Arabic header variants, flagged workspaces only). Everything typed or imported is saved as **draft**; customers see an Arabic name only after a native reader marked it **reviewed** (G2; `LOCALIZATION_NAME_POLICY=human` widens this to merchant/CSV drafts, never AI drafts). AI suggestions are drafts the merchant must confirm.
* **B4 one-word names (flagged workspaces only):** a customer created from a WhatsApp profile name with one word (or none) used to fail `Customer.lastname required` (no customer, no referral attribution). For a flagged workspace the last name becomes a single space (`nameGuard.oneWordLastname`); unflagged workspaces and the kill switch keep today's behaviour exactly.
* **Pages:** the English `/pay/:id` and `/payment-result` pages gain an Arabic switch link (flagged workspaces only); the page language is chosen from `?lang=`, then the stored customer language, then `Accept-Language` (backlog H4); the Arabic Stripe Payment Element is created with `locale: 'ar'`. Referral and Instagram links still 302 to wa.me for English visitors (`?lang=ar` opens the Arabic landing page). There is no opt-in page, booking-confirmation page or customer-facing terms page to translate (consent happens inside WhatsApp; legal documents are merchant-facing). `/payment-cancelled` stays English.

## Webhook journey, same-phone opt-out and Meta error codes (wiring phase, D3)

**Pilot workspace:** see "Turning it on for a merchant" (the webhook resolves every message to the OLDEST workspace; API-originated sends carry the caller's own workspace).

**Outbound localiser (backlog C1, A6, B3).** The English shopping journey after the first tap (catalogue, cards, variants, cart, checkout, pay link, confirmations, points and booking summaries) and the STOP/START/YES/NO replies are English literals in `server.js` and `utils/whatsapp.js`. Instead of ~56 call-site edits, both `waPost` functions call `localization.localizeOutbound(body)` (`shared/localization/outbound.js`). It does something only when ALL hold: kill switch off, the payload is `text`/`interactive` (never a template), the call runs inside the webhook/Stripe handler context (`enterContext(workspaceId)`; transport.js sends are excluded), the context workspace is flagged, the recipient's language is Arabic (customer -> workspace default -> English), the **whole** message matches a catalogued English shape (`journeyMatcher.js`; one drifted word keeps the whole message English), the Arabic text passes the WhatsApp limits and has no unresolved placeholder. Anything else sends the original payload, untouched and with no extra await (an unflagged installation pays one env read, one AsyncLocalStorage lookup and one `Map.has`). Copy: `catalog/journey.json` (86 drafts; `consent.*` and `inbox.*` reused). Draft copy is served unless `LOCALIZATION_ALLOW_DRAFT_PAGES=0`. Product/service names: **reviewed** `ProductTranslation` rows only (`LOCALIZATION_NAME_POLICY=human` also accepts merchant/CSV drafts, never AI ones); an unreviewed or ambiguous name stays as the merchant typed it. The pay link gets `?lang=ar`. Unmatched English sent to an Arabic customer is logged once per message shape as a short hash plus the length (no message text; `LOCALIZATION_DEBUG=1` for detail). A recipient that is not a customer of the context workspace (e.g. another merchant's buyer in the Stripe webhook) always gets English, even when the workspace default language is Arabic. The flag snapshot is stale-while-revalidate (a stale snapshot answers at once and is refreshed in the background; only the very first load is awaited, for at most 1.5 s) and the whole awaited part is raced against a 2 s budget that resolves to the original English payload, so a slow database can never hold a customer reply; `enterContext` skips AsyncLocalStorage when the kill switch is on or the workspace is known to be unflagged. A drift test (`tests/localization/integration/arabicJourney.itest.js`) drives the real handlers and fails when an English string stops matching its shape. Not covered by design: first-contact sends, flow entry messages (D1/D2), merchant free text, the unauthenticated `/payment-cancelled` page, the 22-character English pay-later button label (existing defect: over WhatsApp's 20-character limit; the Arabic label is 18).

**Approved global changes (they affect every merchant, flagged or not - exactly three, plus one detail of the first).**

1. **B2 - Arabic digits, CSV decoding, prices, headers** (`utils/phoneNormalize.js`, `utils/currency.js`, `routes/auth.js`, `routes/workspaces.js`, `routes/internalAdmin.js`, `shared/importEngine.js` + `shared/localization/{arabicText,importDecode,importExtras}.js`). Only inputs that FAILED or were silently wrong before change; every other input is byte-identical (a 5,000,000-comparison fuzz of the phone and price code against the pristine files found 0 differences). (a) A phone typed with Arabic-Indic / Persian digits (a local number, `+٩٦٦ ٥٠ ...`, or mixed `+966 ٥٠ 123 4567` - previously the WRONG number) is normalised in login/OTP request, workspace invites, import duplicate detection and the internal-admin customer search (an Arabic-digit search no longer becomes an empty regex that matched every customer). **O4:** the typed login code also accepts Arabic-Indic digits (`routes/auth.js` OTP verify; ASCII codes hash exactly as before). (b) A BOM-less upload that is strict UTF-8 with Arabic letters/digits gets a BOM; a clearly-Arabic Windows-1256 file is decoded to UTF-8 (xlsx, HTML, UTF-16, Latin-1, accented-Latin-only UTF-8 and files over 5 MB are untouched). (c) `parsePrice` accepts Arabic-Indic digits, separators and Arabic currency words (`١٢٣`, `٤٥ ر.س`; `12٫5` used to be read as 125 and is now 12.5), and Arabic column headers are used as a fallback **only** when no English alias matched. These stay active under the kill switch.
2. **H1 - same-phone opt-out.** `shared/localization/samePhone.js#optOutSamePhone`, called from the three existing opt-out branches of `server.js` (typed STOP/UNSUBSCRIBE, template `optout_` reply, interactive `optout_` button) and from the Arabic hook. Blast radius: triggered only by those events; changes behaviour only when ANOTHER not-yet-opted-out customer record of the SAME workspace has the same normalised number (any stored spelling: `+`, spaces, `00`, Arabic-Indic digits, direction marks, local `05...`); demo records are included, erased records are not; other workspaces are never touched; each sibling gets its own `ConsentEvent` (logged before the change) with the source suffix "(same number, other customer record)"; a failure is retried once and never blocks the reply; replies are unchanged. START still reinstates only the record the sender's phone resolves to (siblings stay opted out). Cost per event: first one workspace-scoped query for the exact stored spellings (international, `+`, `00`, local `05...` and bare national forms using the workspace country code), whose siblings are opted out at once; then a bounded fallback scan for odd spellings (spaces, Arabic digits, direction marks): capped at 20,000 customers (a larger workspace skips the scan and logs once per hour) and at most one scan per (workspace, number) per 60 s, so repeated or forged STOPs stay cheap.
3. **C3 - Meta error code on failed deliveries.** `handleStatusCallbacks` stores `CampaignMessage.errorCode` (a String, additive, absent on older rows) when a status callback is `failed` and carries `errors[0].code`; `statusReason` is untouched. Reader: `shared/localization/statusErrors.js`; the Arabic campaign recipients view shows `errorCode`/`error` for failed deliveries.

## Known limits (details and the open backlog: `INTEGRATION-BACKLOG.md`)

* **Only the oldest workspace is reachable through WhatsApp** (single-workspace webhook, G5) - see "Turning it on".
* **English Automated Flow messages probably cannot be tracked today (IB-13, existing defect, decision G6: report only).** `utils/flowScheduler.js` creates the English flow `CampaignMessage` and `FlowEnrollment` rows without `workspaceId`, while the webhook looks rows up by workspace: delivery/read ticks (`handleStatusCallbacks`), the correlation of a button tap with its flow message (so branching follow-ups after a tap) and workspace-scoped enrollment lists will not find such rows. The Arabic path writes `workspaceId` and works. Whether production rows lack the field has not been checked against the live database. `scripts/backfill-workspace-id.js` (one-time, safe to re-run, assigns every row without a `workspaceId` to the OLDEST workspace) repairs old rows but new ones are created the same way until the scheduler is fixed - an owner decision.
* **Arabic template messages need Meta.** Until a merchant has an Arabic version that Meta approved and a reader reviewed, Arabic customers receive the English message (visible in the plan). No live Meta probe of Arabic templates has been run (backlog F3).
* **Draft Arabic copy is served** to Arabic customers of flagged workspaces (session text, journey, pages, STOP/START answers) unless the two `ALLOW_DRAFT_*` switches are set to `0`; the 17 server strings flagged for the lawyer are among them.
* **A typed Arabic yes/no is accepted as consent** within 24 h of a consent ask (backlog H5, needs the lawyer's decision).
* **Entry-template staleness:** an approved Arabic entry template keeps sending after the English entry message is edited; only follow-ups are gated.
* **Caches:** flag 30 s, customer language 20 s, reviewed-name map 30 s (per server instance).
* **Not translated:** carousel promotions, the fixed default flow messages, referral reward notices, `/payment-cancelled`, the existing English dashboard, Inbox and AI Mode screens (Phase 5), the existing 22-character English "Reserve, Pay in Person" button (over WhatsApp's 20-character limit; the Arabic label is 18), `inbox.updateMessageStatus` (never reached for manual sends - existing dead code).

## Go-live checklist (owner)

1. **Before deploying:** nothing to migrate - the new collections and indexes are created on first use (all small, no unique index on an existing collection). Deploy the backend, then the frontend (a new frontend on an old backend hides its new panels).
2. **Credentials:** set `INTERNAL_ADMIN_USER` / `INTERNAL_ADMIN_PASSWORD` in Azure, or use the CLI. `ANTHROPIC_API_KEY` is only needed for the AI helpers and Arabic AI Mode.
3. **Decide the draft-copy policy** (default: draft Arabic session text is served; see the two `ALLOW_DRAFT_*` variables) and whether to fix IB-13.
4. **Pick the pilot:** find the oldest workspace (command above), flag it, then smoke-test with a phone you control: set its language to Arabic in the profile, grant consent, send a loyalty reminder (the plan screen shows English until an Arabic template is approved), tap a promotion button, send the Arabic opt-out word.
5. **Arabic templates:** create/copy them from the library in `/arabic/templates` (18 entries), submit to Meta, wait for approval (up to 24 h), have a native reader mark them reviewed.
6. **Reviews:** native reader (server catalogue 342 strings, Angular 1,511, plus per-merchant data) and lawyer (the 17 flagged server strings + the two Angular AI strings listed under "Native review").
7. **Rollback:** disable the workspace flag (CLI/admin page), or set `LOCALIZATION_DISABLED=1` for everybody.

## Native review (spec §8)

Every Arabic string starts as **draft**. Three places hold strings: the Angular catalogues (`src/app/i18n/catalogs/ar` + `meta`), the server catalogue (`shared/localization/catalog/*.json`) and per-merchant data (template variants, product names — reviewed inside the UI). Export for a spreadsheet and import back:

```
# screen text (frontend repo)
node scripts/i18n-review.mjs export --out review.csv      # key,english,arabic,status,reviewer,reviewed_at,needs_legal,notes
node scripts/i18n-review.mjs import --in review.csv --dry-run
node scripts/i18n-review.mjs summary --write              # refreshes the counts shown in /arabic/review

# server-sent messages (backend repo)
node scripts/i18n-review.js export --out backend-review.csv
node scripts/i18n-review.js import --in backend-review.csv --dry-run
```

Changed text never becomes "reviewed" by itself — only a row that says `reviewed` with a reviewer name does. Strings flagged `needsLegalApproval` also need the owner's lawyer (never machine-translate legal text).

**Counts on 2026-10-12 (all Arabic is draft; none is reviewed yet).** Server catalogue: **342** strings (`aimode` 96, `journey` 86, `library` 64, `pages` 55, `senders` 17, `consent` 13, `flows` 8, `campaigns` / `inbox` / `templates` 1 each); **17 are flagged for the lawyer** (the 13 `consent.*` acknowledgements/buttons, the 3 Arabic `welcome_optin` library texts, `senders.optOutHint`). Of the 342, about 240 reach customers (`journey`, `pages`, `library`, `senders`, `consent`, `flows`) - that is the native-review priority list. Angular catalogues: **1,511** strings in 19 namespaces (merchant-facing screens), **none flagged** - the AI notice (`ai.notice`) and the AI Mode disclaimer (`aimode.disclaimer`) should be put to the lawyer (spec 4: "wording approved by our lawyer"); the other consent/opt-out strings there are merchant-facing labels and explanations, not legal text. Per-merchant data (Arabic template variants, Arabic product/service names) is reviewed inside the UI, one item at a time. Re-count with `node scripts/i18n-review.js summary` (backend) and `node scripts/i18n-review.mjs summary` (frontend).

## Testing

* **Unit tests** (no database, no network; 76 suites, 6,208 tests on 2026-10-12): `MONGODB_URI=mongodb://127.0.0.1:1/waflow_unit_guard npx jest tests/localization --testPathIgnorePatterns integration --runInBand` (the dead URI is a safety net — never run the *existing* suite against the shared database: it deletes rows and calls real APIs).
* **Integration tests** (`tests/localization/integration/*.itest.js`, 25 suites) write real documents, so they run only against a throwaway local MongoDB, with dummy credentials and no network. Jest's default `testMatch` does not match `*.itest.js`, so `npm test` never runs them. Safe recipe (what the build used):
  1. Start an empty throwaway MongoDB on `127.0.0.1:27099` (for example `mongod --dbpath <empty temp dir> --port 27099 --bind_ip 127.0.0.1`).
  2. Copy the backend to a scratch folder **without** `.env`, `.wa-token-cache.json`, `.claude/` and `uploads/`; link or install `node_modules` there and add a dummy `.env` (every value fake) so no real credential is ever loaded. **Never delete such a folder recursively when `node_modules` is a junction to the real one.**
  3. From that copy, with the network dead and WhatsApp sends in dry-run, **a fresh database name per run** (several suites refuse a non-empty database):

     ```
     HTTPS_PROXY=http://127.0.0.1:9 HTTP_PROXY=http://127.0.0.1:9 NO_PROXY=127.0.0.1,localhost NODE_USE_ENV_PROXY=1 \
     MONGODB_URI=mongodb://127.0.0.1:27099/waflow_loc_test<fresh> LOCALIZATION_SEND_MODE=dry_run AUTH_TEST_MODE=true \
     npx jest --runInBand --forceExit --runTestsByPath tests/localization/integration/<suite>.itest.js
     ```

     `_guard.js` makes every integration test refuse to run unless `MONGODB_URI` is `mongodb://127.0.0.1:27099/waflow_loc_test*`. Wiring-phase suites: `wiringAcceptance` (93 end-to-end tests of the whole combined backend: Phase 1 done-when, promotions, flows, journey, H1, data, pages, C3, kill switch, tenant isolation), `legacySenders`, `flowWiring`, `flowTapE2E`, `arabicJourney` (drift test: fails when an English journey string stops matching its catalogued shape), `samePhone`, `statusCallback`, `dataForms`, `paymentLink`, `pages`.
* **English-unchanged safety nets** (the proof that English / unflagged behaviour is identical): `englishUnchanged2.itest.js` (167 deterministic scenarios over the senders, flows, journey, status callbacks, imports, pages, inbox, GPT actions, auth, internal admin) and the older `englishUnchanged.itest.js` (59 webhook text scenarios). Each boots the real `server.js` with the HTTP layer stubbed (nothing leaves the machine), records every outbound WhatsApp/Graph call (order and full payload) and the normalised database changes per scenario, and compares them with a **golden file recorded on the pristine pre-Arabic backend** (git commit `20082c8`; `ENG_RECORD=1`, only ever on a copy of that commit, repeated until two recordings are byte-identical). The goldens are large and are **not in the repository**: point `ENG_GOLDEN_FILE` at them, or re-record from `git archive 20082c8`.
