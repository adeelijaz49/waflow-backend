## Facts that change the design (verified live against the production WABA, read-only GETs; docs where marked)
1. **Statuses.** Graph `status` ∈ APPROVED, IN_APPEAL, PENDING, REJECTED, PENDING_DELETION, DELETED, DISABLED, PAUSED, LIMIT_EXCEEDED, ARCHIVED. `FLAGGED` is NOT a status (webhook event only). Our enum must be: `NOT_CREATED, PENDING, APPROVED, REJECTED, PAUSED, DISABLED, IN_APPEAL, PENDING_DELETION, DELETED, LIMIT_EXCEEDED, ARCHIVED, ERROR` (+ `metaStatusRaw` string, `metaFlagged` boolean). Unknown Graph values → keep raw text, map to a NON-sendable status, never throw (a Mongoose enum throws on save and would break the poller).
2. **Category.** Meta re-classified BOTH UTILITY templates this app ever submitted (consent request, team invite) to MARKETING (still APPROVED). So: `welcome_optin` is MARKETING with opt_in/decline quick replies; store what Meta reports (`metaCategory`, `metaPreviousCategory`) from the create response/`GET`; **consent gating and audience eligibility use `metaCategory || category`**; a UTILITY→MARKETING flip after approval must force `canSendMarketing` and show a banner. EXCEPTION: the consent-request use case (`welcome_optin`) itself is the ask — it may be sent to customers who have NOT consented (but never to opted-out customers, and not more than once per 7 days per customer), exactly like the existing consent-request flow. **Update 2026-10-12 (UTILITY floor):** on top of `metaCategory || category`, only the transactional use cases (`payment_reminder`, `booking_confirmation`, `booking_reminder`, `order_confirmation`) can ever be treated as UTILITY; every other use case is MARKETING for consent gating whatever category was requested or Meta reports (see `README.md`, "Compliance rules the code enforces").
3. **Leading/trailing variables are rejected by Meta** (error 2388299; documented rejection reason). `body_starts_with_variable` / `body_ends_with_variable` become ERRORS for submission; `arabic_variant_has_no_arabic` becomes an error at submit time. The spec's drafts "Referral invite" and "Payment reminder" need static text added at the ends (Meta's own Arabic templates start with a word and end with a closing sentence).
4. **Bidi marks.** Meta docs are silent; 168/170 of Meta's own Arabic templates contain NO direction marks. → NO direction marks in submitted body/footer/button text or in EXAMPLE values. At SEND time wrap Latin/number PARAMETER values in LRM only when `LOCALIZATION_WRAP_PARAM_LRM=1` (default OFF until a controlled probe is run); never wrap URLs. Make mixed runs safe by sentence design: keep the currency unit in static Arabic text (`{amount} ريال`) or pass the whole amount string. Previews/rendered text for the UI may still use LRM isolation (display only).
5. **Names/lookup.** Names aren't unique across languages; `(name, language)` is. GET filter `name` is a case-insensitive SUBSTRING → always compare exact `name` AND `language` (or `String(id) === metaTemplateId`) client-side. Language filter is exact; a wrong code returns an empty list, not an error. Duplicate CONTENT can be rejected: refuse locally an unchanged resubmission of REJECTED text.
6. **Create response** `{id (string), status, category}` — persist all three; do NOT force PENDING. Errors: read `err.response.data.error.{code,error_subcode,message}`; never log the axios error object (carries the Authorization header). Known creation errors: 100/2388024 duplicate (name,language), 2388040 length, 2388072 body format, 2388293 parameter/word ratio, 2388299 leading/trailing parameter, 80008 rate, 131009.
7. **Polling is primary** (webhook `message_template_status_update` is dropped by the existing handler; no signature check possible): per-variant `GET /{id}?fields=name,status,category,previous_category,language,rejected_reason,quality_score,last_updated_time` and a delta sweep `GET /{waba}/message_templates?since=<lastSweep-5min>&fields=id,name,language,status,category,previous_category,rejected_reason,quality_score,last_updated_time&limit=100` following `paging.cursors.after`; never request `components` in sweeps; rows are newest-first; `rejected_reason` is the string "NONE" when fine (store raw; treat "NONE" as no reason). Poll every 10 min while any variant is PENDING/IN_APPEAL/PAUSED, full sweep daily. Reviews take up to 24 h.
8. **Capacity.** 250 templates per WABA (15 used), 100 creations/hour; the existing `listTemplates()` only reads the newest 100 rows (blind spot for legacy English templates once >100 exist). Every (workspace × use case × language × revision) permanently consumes a slot (delete is forbidden). → expose `{used, limit, ceiling}` (`GET /templates/meta-usage`, via `summary=total_count,message_template_limit`), and REFUSE new submissions when `used >= ceiling` (env `LOCALIZATION_TEMPLATE_CEILING`, default 90) with a clear error (code `META_TEMPLATE_LIMIT`, 409). Show the usage in the Templates tab.
9. **Send errors to map** into `LocalizedSend.errorCode`/`error`: 132001 (template missing in that language / not approved), 132015 (paused), 132016 (disabled), 132000/132012/132018 (parameter problems), 131049/131050 (marketing limit / user stopped marketing), 131047 (outside window), 131026 (undeliverable). Store the code; the report shows a readable reason.
10. **Account facts** (surface in the final report, not in code): business verification `rejected`, messaging tier TIER_250 (≈250 unique customers per 24 h outside the service window) → the campaign planner adds an informational warning `large_audience` when recipients > 250 (detail: count). Bilingual variants are submitted under the FIRST language's code.
11. **Instagram (F3).** Language inference must ignore the prefilled `Code: IG-…` texts (the English prefill makes every Instagram-sourced customer look English). For `/t/:code` choose the Arabic page when `?lang` is absent and the linked post's caption is Arabic (detectLanguage) before falling back to Accept-Language. Caption AI rules: keep #hashtags/@mentions/URLs; the 2,200 limit applies to caption + hashtags + CTA combined.
12. **Referral rewards (F4).** No reward sender exists in English either; do NOT invent a notifier now (it would change product behaviour). The library keeps `referral_reward` as a template the merchant can send manually; the notifier design (poll `ReferralReward{status:'issued'}` + friend `Voucher`, claim-then-send collection) goes to the integration backlog.
13. **Test harness (F2).** Existing-suite regression runs only on a sanitised COPY of the backend with a throwaway mongod and dummy credentials (never `.env`, never `.wa-token-cache.json`, never the Cosmos URI). DB-backed new tests use the suffix `*.itest.js`, guarded to loopback `waflow_loc_test*` databases.
