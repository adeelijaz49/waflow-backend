# WhatsApp onboarding flow - runbook

Status: built 2026-10-15, **OFF by default**. Nothing in this document is needed for the existing app to keep working: with `ONBOARDING_FLOW` unset every response, database write and WhatsApp payload is identical to before the feature existed (review R1 found one cosmetic difference: the default HTML error page Express shows for a 413 or 415 on `POST /webhook` lists a few extra stack-frame lines of the new early layer; the status and the answer are the same).

Related: [META-VERIFICATION.md](META-VERIFICATION.md) (the Meta facts of this build, checked against Meta's current documentation).

## 1. What it is

A guided set-up for NEW merchants, after they subscribe:

1. Subscription access rule (a subscribed workspace unlocks; unpaid / failed / cancelled workspaces are told so, never silently).
2. A 5-step checklist: business details, phone number (Path A: I have a number / Path B: I do not yet), connect WhatsApp (Meta Embedded Signup), approvals checklist (verification, display name, payment method, messaging limit, starter templates), first Promotion.
3. Customers / products prompts, a persistent WhatsApp status strip, notifications (in the app and by e-mail), "Need help?" and analytics.

It is built as NEW files plus five tiny guarded hunks (server.js x4, utils/flowScheduler.js x1). The frontend lives in `waflow-frontend/src/app/pages/onboarding-flow/` (namespace `onboarding` in the i18n catalogues).

## 2. The safety model (why switching it on cannot touch existing merchants)

* Global switch: only `ONBOARDING_FLOW=on` enables anything. Unset or any other value = OFF. It is read on every call, never cached.
* Per-workspace opt-in: a workspace is part of the flow ONLY if it has an enrolled sidecar document (`onboardingstates.enrolled = true`). No document = legacy = never gated, never locked, never redirected.
* Nothing enrols a legacy workspace. Enrolment happens only (a) by staff (page or CLI) or (b) automatically for brand-new self-serve signups, and only when `ONBOARDING_ENROL_FROM` is a valid ISO 8601 timestamp WITH an explicit zone and the workspace was created at or after it. **Always write the value ending in `Z`** (for example `2026-11-01T00:00:00Z`): a date-time without a zone is refused (JavaScript would read it in the server's local time zone, a 3 hour shift between a Riyadh machine and UTC Azure), and so is an impossible date (`2026-02-30` would silently roll over to March) or anything else. A refused value means auto-enrolment stays OFF. The OLDEST workspace (the owner's own, and the one the single-workspace WhatsApp webhook serves) is excluded from auto-enrolment and needs an explicit `--force-oldest` / second checkbox for staff enrolment.
* Un-enrolling is instant and deletes nothing (`enrolled:false`, the rows stay).
* Every staff action is written to `onboardingadminlogs` BEFORE it changes anything (append-only, never deleted).

## 4. Meta dashboard checklist (owner, not code)

- [ ] Tech Provider status: complete the Tech Provider onboarding for the Meta app and request advanced access for `whatsapp_business_management` and `whatsapp_business_messaging` (without it Embedded Signup only works for people with a role on the app; a new-customer cap applies until the business is verified).
- [ ] Facebook Login for Business: create the v4 Embedded Signup **configuration**; copy its id into `META_ES_CONFIG_ID`.
- [ ] Allowed domains: add the WaFlow web app's domain (`FRONTEND_URL`) to the allowed domains / JavaScript SDK domains of the app.
- [ ] App-level webhook: in the app's WhatsApp product, subscribe the callback URL (`<APP_URL>/webhook`) to the fields `account_update, phone_number_name_update, phone_number_quality_update, business_capability_update, account_alerts, message_template_status_update, template_category_update, messages`. Check that `WA_APP_SECRET` is the secret of the app that owns this subscription (signature verification uses it).
- [ ] App settings > Advanced: **Require App Secret** (then set `META_APPSECRET_PROOF=on`; test in `log`/pilot first).
- [ ] **Deauthorize callback URL**: `<APP_URL>/onboarding-meta/deauthorize` (POST).
- [ ] **Data deletion request callback URL**: `<APP_URL>/onboarding-meta/data-deletion` (POST); its status page is `<APP_URL>/onboarding-meta/deletion-status?code=...`. Nothing is deleted automatically (standing rule). Each verified request is recorded once (a retry of the same request gets the same code), support is e-mailed ONCE per request (the notice carries the request id only: no user id, no name, no number; it needs `RESEND_API_KEY` and a support e-mail), and the request is listed as OPEN on the onboarding admin page (`/internal-admin-onboarding`, panel "Meta data-deletion requests") and by `node scripts/onboarding-admin.js list`. Staff process it with the existing `/internal-admin` PII tooling and then mark it: the page's "Mark processed" button (CSRF-protected) or `node scripts/onboarding-admin.js deletion-done <request id> --notes "..."`. Marking writes the admin log FIRST, then sets the request to done; it deletes nothing and is safe to repeat.
- [ ] Both callbacks answer Meta only after the `signed_request` verified: the signature must match `WA_APP_SECRET`, the signature and payload parts must be canonical base64url (one request, one spelling), the algorithm must be `HMAC-SHA256`, an `expires` claim (when Meta sends one) must still lie in the future, and there is no age rule on `issued_at` (Meta's retries stay valid). A request that fails verification is answered 400 and counts toward a per-address limit of 60 FAILED attempts per minute (then 429); a request that verified never passes through that limiter. A replayed deauthorize is recognised by a hash of its payload part.
- [ ] Business verification of WaFlow's own Meta business (raises the onboarding cap).
- [ ] Generate nothing else: merchant tokens come from the Embedded Signup code exchange and are stored encrypted.

## 5. Stripe setup (owner)

1. Recommended: a **separate Stripe account** for merchant subscriptions (hazard below). Put its secret key in `ONBOARDING_STRIPE_SECRET_KEY`.
2. Create the products and recurring prices; put the price ids in `ONBOARDING_STRIPE_PRICES` (`{"growth":"price_..."}`). Prices, currency and plan names are NOT hard-coded in the code or the catalogues.
3. Enable the customer portal in the Stripe dashboard if you want `ONBOARDING_BILLING_PORTAL=on`.
4. Register a **new** webhook endpoint `POST <APP_URL>/stripe-billing-webhook` (its own signing secret, `ONBOARDING_STRIPE_WEBHOOK_SECRET`) with these events and no others:
   `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.paused`, `customer.subscription.resumed`, `invoice.paid`, `invoice.payment_failed`, `invoice.payment_action_required` (`invoice.payment_succeeded` is handled identically if you prefer it). Do NOT subscribe `payment_intent.*` on it.
5. The existing `/stripe-webhook` (shop payments) is never touched.
6. **Shared-account hazard**: if one Stripe account carries both shop payments and merchant billing and the EXISTING `/stripe-webhook` is subscribed to `payment_intent.succeeded`, the PaymentIntents of subscription invoices also reach it (no metadata, no buyer phone), and its WhatsApp confirmation fails and is logged. Harmless noise, but not fixable without touching that handler; a separate Stripe account avoids it.
7. Before go-live run one test-mode checkout end to end (the nested shapes of `name_collection`, `custom_fields` and the period fields under newer API versions are read tolerantly but were not verified against a live account).
8. `subscribed` means: Stripe status `active` with a card on file, OR an explicit admin activation. `trialing` stays pending unless `ONBOARDING_ACCEPT_TRIALING=on` and a default payment method exists. No free-trial path exists (spec 1b.7 is an open owner decision).
9. Payment copy is the neutral line only: "WhatsApp message fees are charged by Meta to your own Meta account." No credits, no re-billing.

## 6. Switch-on procedure (first production use)

Pre-flight (nothing is changed by these):

1. Deploy the code with `ONBOARDING_FLOW` UNSET. Confirm the site behaves as before.
2. From a machine with the production `MONGODB_URI`: `node scripts/onboarding-admin.js list` - expect "No workspace is enrolled" and the owner's workspace marked `[webhook workspace / owner]`.
3. Set the secrets you need in Azure: `WA_TOKEN_ENCRYPTION_KEY`, `INTERNAL_ADMIN_USER`, `INTERNAL_ADMIN_PASSWORD`, `FRONTEND_URL`, `APP_URL`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, and (for Meta/Stripe) the rows of sections 4 and 5. Leave `ONBOARDING_ENROL_FROM` unset (no automatic enrolment) and `ONBOARDING_LEGACY_SEND_POLICY` at its default `block`.

Switch on:

4. Set `ONBOARDING_FLOW=on` in Azure application settings and let the app restart. With nothing enrolled every legacy workspace is unaffected by design (a workspace without an enrolled sidecar document is legacy: never gated, never locked, never redirected). The regression proof is the existing characterisation suites (`tests/localization/integration`) run with the flag on and nobody enrolled: run them before the first production use.
5. **Right after the flag is on, check the indexes in Cosmos DB:** `node scripts/onboarding-admin.js indexes` (it works with the flag off too, so it can also run before step 4; it only reads). The app creates the declared indexes by itself the first time each collection is used, but Mongoose swallows the errors of that build, so a database that refused an index would otherwise be silent. Several guarantees rest on the five UNIQUE indexes: one sidecar and one connection per workspace, one notification per `{workspaceId, dedupeKey}`, one template row per `{workspaceId, key, language}` and one support request per `{workspaceId, kind, 10-minute window}` (the atomic de-duplication of the "Need help?" button). Expect "All declared UNIQUE indexes are present" and exit 0. If it prints "WARNING: UNIQUE INDEXES ARE MISSING" (exit 1), run `node scripts/onboarding-admin.js indexes --create`: it builds exactly the declared indexes (never drops anything, never touches a document) and prints the database's own error for any index that is refused; fix that before enrolling anybody. All nine collections are NEW with this feature (none of them is a collection the existing app uses), so no unique index is ever added to an existing collection, and on an empty collection the build cannot fail on data. Run it BEFORE the first merchant asks for help: every support request carries the `windowKey` of its 10-minute window, and rows without one (written by a build from before this fix; there are none unless the flag was already on in that database) would collide with each other in the unique index (a missing key counts as null). If `--create` reports a duplicate key on `onboardingsupportrequests`, give each of those rows its own `windowKey` (its `_id` as a string is fine) with an update, never a delete.
6. Enrol ONE pilot workspace (sections 8 and 9) and walk through it as that merchant.
7. Only after the pilot is happy, decide on auto-enrolment: set `ONBOARDING_ENROL_FROM` to "now", written as an ISO timestamp ending in `Z` (for example `2026-11-01T00:00:00Z`). Only signups created after that moment are enrolled.

Verify after each step: `node scripts/onboarding-admin.js list` and `status <id>`; the funnel panel on `/internal-admin-onboarding`.

## 7. Rollback

* Instant, no redeploy: `node scripts/onboarding-admin.js unenrol --all --notes "rollback"`. Every enrolled workspace becomes legacy again (rows kept, each change logged). Running servers pick it up within about 30 seconds (gate cache). Use `--dry-run` first to see the count. One workspace: `unenrol <id>` (or the red button on its admin page).
* Full: unset `ONBOARDING_FLOW` in Azure and restart. Nothing is mounted, every hook is its first-statement no-op, the app is byte-identical to before. The data (sidecar documents, connections, notifications, events, logs) stays in the database and is ignored.
* Side effect that is NOT reverted: at enrolment the workspace's `onboarding.completed` was set `true` (so the old wizard does not appear). After un-enrolling a pilot you can set it back with the existing wizard settings if you want the old wizard for them.
* The CLI works with the flag off, so rollback never depends on the flag or on the web page.

## 8. Test a workspace WITHOUT Stripe or Meta configuration

Needs: `ONBOARDING_FLOW=on`, an existing test workspace (NOT the owner's real one unless you really mean it), the CLI (or the admin page with `INTERNAL_ADMIN_*`).

1. Find the workspace id: `node scripts/onboarding-admin.js list` (shows enrolled ones) or the admin page search.
2. Dry run: `node scripts/onboarding-admin.js enrol <id> --dry-run --activate` (writes nothing; it tells you if a safeguard refuses, e.g. existing data needs `--confirm-existing-data`).
3. Enrol and activate in one step: `node scripts/onboarding-admin.js enrol <id> --activate --notes "QA test"`.
   Or two steps: `enrol <id>` then `activate <id> --notes "QA test"` (notes are required; they are the audit trail; this is how partner accounts are activated, spec 1b.7).
4. Check: `node scripts/onboarding-admin.js status <id>` shows subscription `active (source admin)`.
5. Log in to the app as a member of that workspace. The setup page (`/setup`) replaces the old wizard for this workspace only.
6. Undo any time: `deactivate <id>` (back to the billing screen), `unenrol <id>` (back to legacy).

What you CAN exercise this way:
* Step 1 (business details) and Step 2 (number path A: four branches with the right guidance; path B: pause, resume with "I've got my number", "ask WaFlow to help me get a number" support request).
* The billing screen for an enrolled but not activated workspace (checkout shows "contact us" while `ONBOARDING_CHECKOUT` is off), the 402 lock of sending routes, the persistent status strip, notifications (the bell, mark as read), the customers / products prompts (done needs real data, skip always works), the first-Promotion hand-off data (read only), analytics and the funnel panel, the admin page and CLI themselves, Path B reminders (the scheduler sends them at +24 h, +3 d, +7 d by e-mail and in the app; they need `RESEND_API_KEY` for the e-mail part).
* "Refresh connection now" and "Reconcile billing now" refuse politely when there is no connection / no Stripe subscription.

What you CANNOT exercise without configuration:
* Step 3 (connect WhatsApp): needs `META_ES_APP_ID`/`WA_APP_ID`, `META_ES_CONFIG_ID`, `WA_TOKEN_ENCRYPTION_KEY` and a real Meta Tech Provider setup; without them the screen shows the "not available right now, contact us" state (`CONNECT_NOT_CONFIGURED` / `ENCRYPTION_NOT_CONFIGURED`).
* **To test Step 3 end to end use a SEPARATE WhatsApp Business account** (its own WABA and its own number, for example a Meta test account), never the platform's own. The platform's account (`WA_WABA_ID` / `WA_PHONE_ID`) is refused by design: connecting it is answered `CONNECT_NUMBER_IN_USE_BY_OTHER_ACCOUNT` before anything is claimed, stored or written to Meta, and no other onboarding code touches it either (section 11).
* Step 4 (approvals), starter-template submission and the test message: need a connected WhatsApp Business account (a separate one, as above).
* A real checkout and the payment-failed / reactivation e-mails: need Stripe (use Stripe test mode).

## 9. Staff tooling cheat sheet

Page `/internal-admin-onboarding` (Basic auth; mounted only while the flag is on): search a workspace, see enrolment, subscription (state, source, raw Stripe status, period end), progress with per-step timestamps, number path, connection with a MASKED number and token-health flags only (never the token or PIN), template statuses, the last 20 events, open support requests, unmatched Stripe events, the open Meta data-deletion requests (panel "Meta data-deletion requests": open first, each with a "Mark processed" form; section 4) and the funnel. Actions: Enrol (red banner and a second checkbox for the OLDEST workspace, another for existing data), Un-enrol, Admin-activate (notes required), Admin-deactivate, Refresh connection now, Reconcile billing now. A "No e-mail on file" warning marks phone-only accounts (they get in-app notifications only). Forms carry a per-day CSRF token keyed by `INTERNAL_ADMIN_PASSWORD`; without that variable no button is shown.

CLI (works with the flag off; exit 0 ok, 1 refused/failed, 2 bad usage; admin identity `cli:<os user>`; the connection string is never printed):

```
node scripts/onboarding-admin.js list
node scripts/onboarding-admin.js status     <workspaceId>
node scripts/onboarding-admin.js enrol      <workspaceId> [--activate] [--notes "..."] [--force-oldest] [--confirm-existing-data] [--dry-run]
node scripts/onboarding-admin.js unenrol    <workspaceId> | --all   [--notes "..."] [--dry-run]
node scripts/onboarding-admin.js activate   <workspaceId> --notes "Riyadh partner" [--dry-run]
node scripts/onboarding-admin.js deactivate <workspaceId> [--dry-run]
node scripts/onboarding-admin.js funnel
node scripts/onboarding-admin.js deletion-done <requestId> [--notes "..."]
node scripts/onboarding-admin.js indexes [--create]
```

* `list` also shows the OPEN Meta data-deletion requests (request id, when it was received, the workspace when the request named a known Meta user). Nothing is deleted automatically: process the request with the existing PII tooling, then `deletion-done <requestId>` (the id is the confirmation code Meta was given; the admin log row is written first, the request becomes done, nothing is deleted, repeating it is harmless; exit 1 for an unknown id).
* `indexes` lists the indexes of the nine onboarding collections and warns loudly (exit 1) about every missing UNIQUE one; `--create` builds the declared indexes explicitly (it never drops an index and never touches a document) and prints the database's error for any index that is refused. Run it right after the flag is switched on in Cosmos DB (section 6, step 5).

## 10. Notifications, e-mail and reminders

* Every notification is one row in `onboardingnotifications` with a unique `{workspaceId, dedupeKey}`: the same event twice = one row, and the e-mail goes out on the FIRST insert of a key only. The in-app row always exists; the e-mail is best effort: a failure is recorded on the row, retried by the scheduler, and never blocks the state change. A mail is attempted at most 3 times in all (the first try plus two retries). "No recipient" (a phone-only account with no e-mail address) and "e-mail not configured" (`RESEND_API_KEY` unset) are recorded as skipped and never retried; the in-app notification is still there.
* **Which notifications send an e-mail** (spec Step 4: "Send an email and an in-app notification when anything changes (approved, rejected, needs action)"). Each call site decides; this table is the whole policy:

  | Notification kind | E-mail | Raised by |
  |---|---|---|
  | `payment_failed`, `subscription_active`, `subscription_cancelled` | yes | the signed Stripe billing webhook |
  | `connected` | yes | a completed connection (a connect, a resume or a reconnect that completes; a replay of a finished attempt sends nothing) |
  | `reconnect_needed` | yes | token revoked or expired, partner removed, deauthorize, disconnect by the owner |
  | `verification_changed`, `display_name_decided`, `messaging_limit_changed` | yes | the status refresh (poll or webhook), once per real change |
  | `account_alert` | yes when its severity is `warning` or `action` (a critical or warning alert, a violation or restriction, a cause that needs the merchant); an informational alert stays in the app, and so does the alert that only repeats a declined display name (that decision has its own mail) | the status refresh and the Meta account webhooks |
  | `template_rejected` | yes, one per template id and status | template status events (webhook or poll) |
  | `template_approved` | **per template: in the app only.** Two milestone notifications of the same kind carry the e-mail (next bullet) | template status events |
  | `pathb_reminder` | yes (+24 h, +3 d, +7 d) | the Path B reminder sweep |
  | `sending_paused` | no, in the app only (the `payment_failed` mail already covers an unpaid workspace) | the flow scheduler hook |
  | `help_received` | no, in the app only (staff get the support e-mail below) | a help request |

* **Template approvals are coalesced.** The 7 starter templates (x English and Arabic) must not send up to 14 mails in a burst. Every approval is one in-app notification WITHOUT an e-mail; on top of that exactly two milestone notifications (kind `template_approved`, generic in-app text, params `{ count, total }` only: no template name) send the mail, each at most once per workspace: `templates:first_approved` (the first starter template is approved) and `templates:all_approved` (every non-blocked English starter template is approved; the Arabic ones do not hold it back). If the first approval is also the last one only the "all approved" mail is sent. The internal setup test template never counts. A rejection is not coalesced: one mail per rejected template.
* **Billing-exempt routes.** `GET /api/onboarding/notifications`, `POST /api/onboarding/notifications/read` and `POST /api/onboarding/events` (gate E) answer for ANY enrolled workspace whatever its subscription state (none, pending, past_due, cancelled), so the bell keeps showing the payment problem and the analytics beacons keep working while a payment is overdue or after a cancellation (spec 1b.5: the merchant keeps access to data and progress). A workspace that is not enrolled still gets the 404 `ONBOARDING_NOT_AVAILABLE`, and every other step route stays closed with its 402 code until the subscription is active (`/state`, `/help-context`, `/checkout`, `/billing-portal` and `/billing/refresh` are the other routes that work in any enrolled state).
* E-mail recipient: Stripe checkout e-mail (`prefill.email`), else the owner's login e-mail, else the optional "Email for updates" typed in Step 1 (stored as `business.contactEmail`; the Step 1 screen offers the field, it can be left empty); none = in-app only. **That field is OWNER-ONLY** (the platform sends system e-mail to it): the server re-reads the Membership of the requester, and for anyone else (a member, a removed member whose token still says owner) the address is silently dropped while the rest of the request is saved. An address counts for notification mail only when the owner typed it (`business.contactEmailByOwner`); a value without that marker (older data) is not used until the owner submits it again in Step 1. Language = the merchant's chosen UI language. Mails are English + Arabic (Arabic is a DRAFT until a native reader reviews it), every dynamic value is HTML-escaped, subjects are static, and no mail contains a phone number, token, workspace name or template name.
* **Starter templates are submitted at once after a connection.** A completed connection (a connect, or a resume or reconnect that completes) hands the first 5 queued starter templates to Meta right away (`starterTemplates.submitQueued`, best effort, never awaited by the answer) instead of waiting for the next scheduler tick (up to 10 minutes, 5 per tick). It is skipped for a connection that still lacks its number and for an enrolled workspace whose subscription is not active; a failure is logged with its code only and never changes the connect answer or its replay. Submission is claim-protected, so this call and a scheduler tick can never submit a template twice.
* Path B reminders (merchant has no number yet): +24 h, +3 d, +7 d after the pause, then stop; they also stop as soon as "I've got my number" is pressed. Delivered by e-mail and in the app, never through WhatsApp.
* Support: "Need help?" requests are stored in `onboardingsupportrequests` and e-mailed (escaped) to `ONBOARDING_SUPPORT_EMAIL` or `SUPPORT_DESK_EMAIL`. The button is limited three ways: at most 10 calls per workspace per 10 minutes (in memory, per instance; beyond that 429 `RATE_LIMITED`), at most 3 requests per day per workspace and kind (counted in the database), and ONE request per workspace, kind and 10-minute window: every row carries its window key and the unique index `{workspaceId, kind, windowKey}` lets exactly one of any number of simultaneous clicks create it (the others are answered with that row, `duplicate: true`, and no second e-mail or notification is made). The index is built by the app on first use; check it with `indexes` (section 6, step 5).
* **Recurring conditions notify again.** The dedupe key of a notification about a condition that can come back (verification, display-name decision, messaging limit, a connection that needs attention, a subscription that became active or cancelled) ends with an epoch: the version of the connection document (or the time of the Stripe event) that caused it. The "reconnect needed" key already carries the time of the connection, which every reconnect changes. Two servers handling the same change write the same key and make ONE notification; a later recurrence of the same condition is a new key and tells the merchant again.
* **The setup test message** ("Send me a test message" in Step 5) goes from the merchant's own WhatsApp number to the REQUESTER's own login phone (`User.phone`). A typed number is accepted only when it is that phone (otherwise 422 `TEST_PHONE_INVALID`, reason `NOT_YOUR_NUMBER`); nobody can message a stranger through it. A user who logs in with an e-mail address and has no phone is served only when they are the workspace OWNER (a live Membership read): the owner types ONE number, which becomes the workspace's test number (stored masked plus a hash keyed with `AUTH_JWT_SECRET`, never the digits; every later request must be the same number or is refused with `TEST_NUMBER_FIXED`, and the owner types it again each time because the digits are not kept). A member without a phone gets 403 `OWNER_ONLY`; `GET /first-promotion` says `testRecipient.needsPhone: true` only for such an owner. Without `AUTH_JWT_SECRET` no hash is stored: only the last 4 digits and a counter are kept, and two numbers that share their last 4 digits count as the same. Only an APPROVED **UTILITY** template is ever sent (the setup test template first, then any other approved UTILITY template; a template Meta re-categorised as MARKETING never qualifies and no marketing template is a fallback): with none approved yet the answer is 409 `TEST_NO_APPROVED_TEMPLATE`. Unchanged limits: 5 sends per hour per workspace (`TEST_RATE_LIMITED`), 2 distinct numbers per workspace lifetime (`TEST_NUMBER_LIMIT`), and a number that belongs to an opted-out customer of the workspace, in any stored notation, is refused (`TEST_RECIPIENT_OPTED_OUT`).
* **Routes that spend the merchant's Meta credentials re-check the membership.** The test message, template submit and resubmit, `POST /connection/refresh` and `POST /approvals/payment-confirmed` read the Membership of the requester on every call (the login token is valid for 30 days and says nothing about a removal): someone who is no longer a member of the workspace gets 403 `NOT_A_MEMBER` before anything is read, sent or counted against the rate limits. The display-name change was already owner-only, also from a live read.
* The scheduler needs `ONBOARDING_FLOW=on`; it takes a database lock so several instances do not double-send.

## 11. Known limitations (read before promising anything)

* **Sending is not multi-tenant.** The existing senders still use the platform WhatsApp number. Connecting a merchant's own number does not make the existing screens send from it. Under the default policy `block`, legacy sends of an ENROLLED workspace are refused with the visible code `SENDING_NOT_AVAILABLE_YET`; `platform_number` is an explicit owner opt-in for supervised pilots. A separate multi-tenant sending phase is needed (estimate 8-12 working days).
* **Webhook signature safety and bounds (orchestrator rulings 1 and 2, review R1).** With the flow on and the signature mode not `off`, the new middleware takes over `POST /webhook` ONLY for conforming JSON: `Content-Type: application/json` with a body, no `Content-Encoding` header at all (not even `identity`) and no charset other than UTF-8. Every other request (urlencoded, text/plain, octet-stream, gzip or deflate bodies, other charsets, no body) is handed to the existing parser untouched and is answered exactly as it is today, and so is every request when the flag is off or the mode is `off`. A conforming body is read once as raw bytes so the `X-Hub-Signature-256` header can be checked against `WA_APP_SECRET`; a body that is not valid JSON is passed to the existing error path as the same 400 parse error the existing parser raises.
  * **Size.** Meta always signs. With the signature header the body may be up to 3 MB (Meta's own payloads are far smaller; above that: 413). WITHOUT the header the legacy limit of 100 kB applies: a larger declared length is left to the existing parser, which answers 413 as it always did; a body with no declared length is cut at 100 kB and answered 413 by the middleware itself. An anonymous caller can therefore never make the process buffer 3 MB.
  * **What is examined.** A request is answered `403` ONLY when BOTH are true: the payload POSITIVELY matches a merchant `WhatsAppConnection` (an entry id, or a `metadata.phone_number_id`, found through the memoised lookup the merchant-event interception uses) AND its signature is invalid or absent. Every other payload passes through to the existing handler unchanged in EVERY mode: the platform's own payloads, payloads without an entry id, payloads for a WABA nobody owns, and any payload for which the lookup fails or takes longer than 1.5 s (database error = pass through). A payload WITHOUT a valid signature is examined for its FIRST 20 entries only (the existing handler reads `entry[0]` only); the entries after them stay in the payload untouched and are never looked up, processed, claimed or counted, and an unsigned entry never writes a row to the (never deleted) ledger: at most one tiny "please poll" write per workspace per 30 seconds. A payload with a VALID signature (only Meta can make one) is examined for up to 1,000 entries, each DISTINCT id looked up once, and at most 200 changes per entry are read. Only digit-only ids of 5 to 30 characters are ever looked up or remembered (anything else is simply "not a merchant"); the 60 s memo holds at most 2,000 ids (expired ones leave first, then the oldest); unsigned traffic shares a budget of 300 uncached lookups per minute and process. The existing handler acknowledges Meta with 200 first and the valid entries are handled afterwards, so a large signed payload is processed after the answer.
  * `log` mode only logs (one throttled line per minute, no content, no secret) and never rejects. A mis-set `WA_WABA_ID` or `WA_APP_SECRET` can never break the owner's live webhook (a wrong `WA_APP_SECRET` only makes merchant payloads fail their signature check). With `WA_APP_SECRET` unset, merchant payloads are unsigned hints (nothing is trusted, nothing is rejected). Recommended roll-out: `ONBOARDING_WEBHOOK_SIGNATURE=log` first, then `enforce`.
* **Hot-path hooks fail open after 1.5 seconds.** The onboarding checks that sit in front of existing behaviour (the HTTP gate of the send and connect routes, the interception of merchant webhook events, and the "is this workspace allowed to send" check that the flow scheduler uses to skip the flows of a paused workspace) wait at most 1.5 s for the database. When it does not answer, the existing behaviour simply goes on (the request is let through, the webhook reaches the existing handler, the flow sweep continues), nothing is cached from that failure, and one line per minute and per hook is logged with the error code only. The legacy app can therefore never hang because the onboarding collections are slow or unreachable. (A database that ANSWERS with an error is a different case: the gate cache's last known answer is used, see "The gate cache" below; one that does not answer at all is let through after 1.5 s.)
* **The platform's own WhatsApp account can never be connected by a merchant.** `WA_WABA_ID` and `WA_PHONE_ID` identify it. A connection attempt whose popup report names it, or whose token turns out to own it, is refused with the existing code `CONNECT_NUMBER_IN_USE_BY_OTHER_ACCOUNT` (the neutral wording of any number in use; it does not say whose account it is) BEFORE any claim, stored id or Graph write; the exchanged token is not kept and nothing is resumable. For an account that holds those ids anyway (the env was set after the connection), no code path subscribes, unsubscribes, registers, renames, submits templates to or sends a message through it: disconnect skips the unsubscribe (that would remove the production webhook subscription), the status refresh does not re-subscribe, the display-name change and its re-registration sweep refuse, and the starter templates and the test message treat it as "not connected". Test connecting with a SEPARATE WhatsApp Business account (section 8).
* **Connecting claims only what was verified.** The phone number id that the browser reports is only a hint: the account's own number list (`listPhones`) must contain it and Graph must return it before it is claimed (`WhatsAppClaim`, one row per id, cross-tenant) and stored; otherwise the run stops with `CONNECT_WABA_MISMATCH` and nothing is claimed, so nobody can squat on another account's number. Claims are released, never deleted (`releasedAt` is set): a run that fails gives back the claims it took, a resume takes them again from the stored ids, and if another account took the number in between the resume stops with `CONNECT_NUMBER_IN_USE_BY_OTHER_ACCOUNT`. Whether the number still has to be registered is decided on the live status of THIS number at Meta (`CONNECTED` = no register call, any other reported status = register); a record of an earlier registration counts only when Meta reports no status at all.
* **Connecting a different WhatsApp Business account (or number) starts clean.** If the connection row held another WABA, what belongs to that account does not carry over: the payment confirmation (back to "unknown"), the business verification, the health report and the business id, together with everything that belongs to the number (below); the starter-template rows are queued again for the new account (revision 1; every template row now stores the WABA it was submitted to). A different number in the same account resets only what belongs to the number: its registration and the PIN, the display name, the quality rating and the messaging limit. Reconnecting the same account and number resets nothing.
* **A refresh never undoes a disconnect.** The status refresh writes its result only if the connection row is still the one it read (same status, same disconnect time, same last token check); a disconnect, reconnect or other refresh that happened while Graph was answering makes it drop the stale result instead of overwriting it, and a revoked-token answer arriving after a disconnect does not flip the row to "reconnect needed".
* **Booking / order status notices still go from the platform number** (best-effort side effects of booking and order status routes; they are deliberately not blocked, otherwise the state change itself would stop).
* **More senders that still use the platform number and are NOT paused for an unpaid or cancelled enrolled workspace** (decision D19: service-level hunks are a later phase). Besides the booking / order notices above: the referral reward messages (`shared/referrals.js`, sent by its periodic reconciliation, every 5 minutes by default), the payment confirmations of `routes/pay.js` (and those of the existing `/stripe-webhook` handler), and the automatic replies of the legacy `POST /webhook` handler to customers who answered a message. What IS paused: the active flows (hunk E5 in `utils/flowScheduler.js`, with a visible trail) and the send / connect routes listed in `shared/onboarding/sendRoutes.js`. Instagram scheduled publishes (`shared/instagram.js`) are not paused either; they are not WhatsApp messages, and only the connect, disconnect, schedule and publish-now routes of `sendRoutes.js` are gated (the subscription only).
* **The bell shows the milestones next to the approvals.** The two milestone notifications of section 10 use the same catalogue text as a single approval ("A message template was approved"), so the in-app list shows them beside the per-template entries; the e-mails (which carry the counts) are what tells them apart.
* Inbound messages to a merchant's own number are acknowledged and dropped (counted), merchant inboxes are not part of this build.
* `ONBOARDING_STRICT_LOCK` is reserved and NOT implemented: the variable is read by `config.strictLock()` but nothing enforces it (the server enforces sends and connects only; setting it changes nothing).
* **Display name:** Meta documents `name_status` as beta. When Meta never returns it, the Step 4 display-name row stays "we are checking" (waiting). It never blocks anything: every Step 4 row is non-blocking, setup can finish with step 4 open, and an unknown name does not keep the 15 minute status poll alive.
* **Erased customers** (the internal admin tool sets `Customer.deletedAt`) are never counted toward the customers prompt "done", the counts of `/state` or the audience of the first Promotion hand-off.
* The downloadable customers CSV template is header only (no sample rows), so an untouched template can never import a fake, opted-in customer.
* **No CR (commercial registration) document upload**: only the number is stored (existing uploads are public URLs). Deviation from spec Step 1.
* Saudi **coexistence** (same number on the WhatsApp Business app and the API) availability is unverified; the guidance never promises it.
* Meta business-token **lifetime is unverified**; handled by token-health polling (needs-attention below 7 days) and a reconnect flow.
* No free-trial path; Stripe Checkout has no Arabic locale (browser locale is used).
* The gate cache lives per instance: up to 30 s for an enrolled workspace and up to 60 s for a workspace that was answered "not enrolled" (an enrolment made on another instance shows up within that time), and up to 10 minutes of the last known answer while the database cannot be read. `/state` and `/billing/refresh` bypass it; a change made on the same instance invalidates it at once.
* Dedupe, event and audit collections grow without TTL or deletes (tiny volume, by the no-delete rule).
* **Scaling notes (review R7-10: known, deliberately NOT built).** Everything the scheduler reads is bounded by a `limit` and at most a single-field sort, and one tick runs per `ONBOARDING_SCHEDULER_INTERVAL_MS` (10 minutes) under a database lock, so only one instance sweeps at a time and extra instances add no throughput. The tables hold one row per enrolled workspace (16 rows per workspace in the template table), so the scans below cost little at pilot volume. When enrolled workspaces grow into the thousands, or a sweep shows up in the Cosmos DB request-unit metrics, add the indexes below: declare each with `schema.index(...)` in its model, run `node scripts/onboarding-admin.js indexes --create`, and read the error line it prints (Cosmos DB can refuse some index shapes; creating an index never drops or changes a document).

  | Sweep and what it reads | Index today | Index to add later |
  |---|---|---|
  | Connection status refresh: `status in (connected, needs_attention, ...) and nextCheckAt <= now`, oldest first, plus `nextCheckAt: null` | `whatsappconnections { nextCheckAt }` | none |
  | Webhook lookup of a merchant by WABA or phone id | `whatsappconnections { ids.wabaId }`, `{ ids.phoneNumberId }` | none |
  | Template status poll (`metaTemplateId` set, `metaStatus` pending, `lastCheckedAt` old; 500 rows per tick) and the queue read of the submit sweep (`blockedReason: null, metaTemplateId: null, attempts < max`) | only the `{ workspaceId, ... }` indexes: a collection scan | `onboardingtemplates { metaStatus, lastCheckedAt }` and `{ blockedReason, metaTemplateId }` |
  | E-mail retry: failed mails with `emailAttempts < 3` (20 per tick) | none: a collection scan | `onboardingnotifications { emailSentAt, emailAttempts }` |
  | Resume of stuck `connecting` runs (20 per tick) | none | `whatsappconnections { status }` |
  | Stripe reconcile: `subscription.state` pending, or active / past due with an old `subscription.stripe.lastSyncedAt` | `onboardingstates { subscription.stripe.subscriptionId }`, `{ subscription.stripe.customerId }` | `onboardingstates { subscription.state, subscription.stripe.lastSyncedAt }` |
  | Display-name re-registration (`displayName.decision = APPROVED`, 20 per tick) | none | `whatsappconnections { displayName.decision }` |
  | Path B reminders (`progress.status = paused_number`) | `onboardingstates { progress.status }` | none |
  | Staff funnel (`enrolled != false`, bounded read, plus the event aggregation) | events by `{ type, code }`, `{ type, step }`, `{ workspaceId, at }` | `onboardingstates { enrolled }` |

  Collections that only grow (no TTL, no delete: the standing rule): `onboardinginbounds` (the dedupe ledger), `onboardingevents` (capped per workspace: 400 events, and the types that explain why something stopped, namely step failures, blocked sends, status changes, payment states and connect results, continue until 600; `webhook_dropped` rows are not part of that budget, are written once per workspace, code and UTC day, and stop at 400), `onboardingadminlogs`, `onboardingsupportrequests` and `onboardingnotifications`. Add a TTL or an archive job only as an explicit decision to delete data. If one instance ever becomes too slow for the sweeps, the sweeps would need a partitioned design: more instances alone do not help.
* Display-name length limits (3 to 512) are unverified; Meta applies its own rules and the result is shown as-is.

## 12. Pre-existing exposures found and deliberately NOT touched (report only)

1. `POST /send-message` is unauthenticated.
2. The platform `POST /webhook` has no signature verification (new code only verifies payloads of connected merchant WABAs; every other payload is passed through unchanged, `log` mode reports mismatches).
3. `/api/whatsapp/*` (template create/delete, token refresh) is open to any workspace member.
4. The `isDemo` customer exemption from the consent filter plus `send-live-demo`: marketing-opt-in is therefore not unconditional today.
5. `Subscription.status` defaults to `active` and is created lazily (the legacy subscription model is not used by this flow; activation is NOT mirrored into it).
