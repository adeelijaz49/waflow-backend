# Meta and Stripe verification report: WhatsApp onboarding build

Written for the owner. Plain English first; engineering detail is in the last column of each table. Documentation only: no code or setting was changed.

- **When:** Meta facts were researched on 2026-10-15. For this report (2026-10-23) the most time-sensitive Meta pages and the six Stripe pages named in section 1 were read again; those facts carry **(R)**. Anything that changed after the first research is marked **NEW**.
- **Not tested live:** nothing here was run against a real Meta or Stripe account. The whole build is tested with mocks only.
- **Confidence:** **HIGH** = stated on a current Meta or Stripe page we read. **MEDIUM** = third-party or summary only, one page only, or two pages disagreeing. **LOW / UNVERIFIED** = could not be confirmed (a guess, or from memory).
- **Where the code is:** backend `waflow-backend/shared/onboarding/` (`metaConfig.js` holds every Meta constant with its confidence tag, `metaErrors.js` the error table); frontend `waflow-frontend/src/app/pages/onboarding-flow/`. Settings and runbook: `docs/onboarding/README.md`.

## The short version

Where Meta's current documentation differs from the prompt (details in section 2):

1. **Embedded Signup version.** Build on v4: v2 and v3 were deprecated on 2026-10-15. **NEW (R):** Meta released v5 on 2026-10-20. v4 still works and has no end date, so the code stays on v4. Moving to v5 is a separate change: the v5 result has no `waba_id` (the browser adapter and the connect step read it) and v5 switches coexistence on by default (the coexistence copy would need review).
2. **The one-time code** from Meta's popup lasts 30 seconds and is treated as single use. The app sends it to the server immediately.
3. **Payment method:** Meta documents no way to read whether a merchant added a card. That row is self-attested ("I've added my card").
4. **Messaging limits** belong to the whole business portfolio: 250 to start, then 2,000. The app shows what Meta reports and promises no number.
5. **Pricing:** on 10-15 Meta's two pricing pages disagreed. **NEW (R):** they now agree that service replies and in-window utility templates are charged from 2026-10-01 (the main page adds a monthly free allowance of service replies). The copy stays neutral and never calls messaging free.
6. **Coexistence** (one number on both the WhatsApp Business app and WaFlow) in Saudi Arabia is still undocumented either way (re-checked 10-23). The copy promises nothing.
7. **Webhook signature:** the existing `/webhook` never checked Meta's signature, so there was nothing to "keep". New checks cover connected merchants only; your live webhook's traffic passes through unchanged.
8. **Meta access:** to onboard merchants WaFlow's app needs advanced access (the Tech Provider route); without it only people with a role on the app can connect. Meta also caps new businesses at 10 per rolling 7 days, raised to 200 once WaFlow's own business verification, app review and access verification are complete.
9. **Account model:** Meta is splitting the WhatsApp Business account into a "WhatsApp account" and a "Messaging account". Existing IDs keep working; no change is needed now.

**Only a real pilot merchant can settle:** whether Meta needs a `redirect_uri`, how long a token lasts, whether registering a number still needs a PIN, coexistence in Saudi Arabia, whether Meta returns the display-name status, and which Meta web address the popup messages come from.

**Found while writing this report (not Meta facts):** (a) the browser accepts popup messages from only two Meta addresses, narrower than Meta's own sample; (b) the display-name tip and "It's free to create" are unverified claims in merchant text; (c) when Meta rejects the code exchange, whatever the reason, the merchant is told "the code expired", and nothing is logged for Meta error 100; (d) the backend and frontend default links for WhatsApp Manager differ. See sections 2 and 5.

**Recommendation:** run one real pilot before any paying merchant; go live on v4 and plan v5 afterwards; remove the unverified copy lines until checked; settle the website's pricing wording (Meta's side is now clear; the rates themselves are only in Meta's rate cards, which were not read).

## 3. Stripe

**Verified on docs.stripe.com (all re-read 2026-10-23).**

| Fact | Where the code relies on it |
|---|---|
| Signature check needs the raw, unmodified body, the `Stripe-Signature` header and the endpoint secret (`constructEvent`) [HIGH, R] | `stripeAdapter.verifyEvent`; new endpoint `POST /stripe-billing-webhook` mounted with a raw-body parser before `express.json()`; a bad signature gets 400. |
| Failed deliveries are retried up to 3 days; the same event can arrive twice (sometimes as two events: compare object id plus type); order is not guaranteed [HIGH, R] | Each event id is claimed before processing; state is read from Stripe, not from event order. |
| A secret can be rolled with the old one active for up to 24 hours [HIGH, R] | `ONBOARDING_STRIPE_WEBHOOK_SECRET` and `_PREV` are both accepted. |
| Recommended subscription events: `customer.subscription.created/updated/deleted/paused/resumed`, `invoice.paid`, `invoice.payment_failed`, `invoice.payment_action_required`; `checkout.session.completed` for Checkout; `invoice.payment_succeeded` is not on the subscription page (older name) [HIGH, R] | Allow-list of exactly those nine plus `invoice.payment_succeeded` (handled the same); everything else is ignored. Register `invoice.paid`. Never `payment_intent.*`. |
| After `invoice.paid`, fetch the subscription and check it is `active` before granting access [HIGH, R] | `subscriptions.retrieve` for every event except `customer.subscription.deleted`; only the fetched status counts (the event payload is a fallback for `customer.subscription.*` only). |
| A redirect to the success page is not proof of payment; webhooks are. Stripe also suggests re-checking from the landing page [HIGH, R] | The success URL changes nothing; the page polls the server. `POST /api/onboarding/billing/refresh` re-reads from Stripe (rate limited; off with `ONBOARDING_BILLING_RECONCILE_ON_DEMAND=off`). Only a webhook, a Stripe re-read or admin activation makes a workspace "active". |
| Statuses: `trialing`, `active`, `incomplete` (23 hours to pay), `incomplete_expired`, `past_due`, `canceled` (final), `unpaid` (revoke access), `paused` [HIGH, R] | `subscription.js`: active = active; trialing and incomplete = pending (no free-trial path; trialing counts only with `ONBOARDING_ACCEPT_TRIALING` AND a card); past_due, unpaid, paused = past due; canceled = cancelled; incomplete_expired = none; an unknown status changes nothing and is logged. |
| Checkout parameters used: `mode=subscription`, `client_reference_id` (max 200), `metadata` and `subscription_data`, `customer_email` (max 800), `custom_fields` (max 3), `payment_method_collection` (default `always`, subscription mode only), `success_url`, `cancel_url`, `expires_at` (default 24 h) [HIGH, R; `subscription_data.metadata` per the 10-15 notes] | `stripeAdapter.buildCheckoutParams`; price ids come from `ONBOARDING_STRIPE_PRICES`, never from the browser. |
| **No Arabic Checkout:** the `locale` list (41 values, `auto` included) has no `ar`; blank or auto follows the browser [HIGH, R] | No `locale` is sent. Arabic merchants get browser-language Checkout (owner decision, see runbook D21). |
| Billing portal: `billing_portal.sessions.create` with `customer` and `return_url` returns a short-lived `url`; the portal must be configured in the Dashboard first, separately for test and live [HIGH, R] | `billing.js`: `BILLING_PORTAL_UNAVAILABLE` if disabled, no customer, or Stripe refuses. |
| **NEW (R):** when creating the endpoint, Stripe's Dashboard recommends "Thin" events for new integrations and also offers "Snapshot" [HIGH, R] | The code reads classic events (`event.data.object`): choose **Snapshot**. |

**Left tolerant or unverified (test-mode run before go-live):**
- Business-name capture: `name_collection` exists and can collect business names, but its inner keys were not readable. The code uses a custom text field `business_name` instead (response path `custom_fields[].text.value` unverified).
- Period end under newer API versions (on the subscription itself or on each item): not confirmed on the pages re-read; the reader tries both places. If it is missing, only the stored period end (shown on the staff admin page) is empty; access never depends on it.
- Invoice-to-subscription link: `invoice.parent.subscription_details.subscription` from API 2025-03-31.basil, `invoice.subscription` before; both shapes confirmed (R), and the reader tries both. The code pins no API version, and Stripe says the account or endpoint API version decides what events look like.
- `subscription_data.metadata` landing on the subscription: from the 10-15 notes; collapsed on the re-read. The first live checkout and the portal configuration state are untested.
- Delayed payment methods (bank debits): `checkout.session.async_payment_*` events are not subscribed; the later change is expected to arrive as `invoice.paid` or `customer.subscription.updated` (our inference).
- Shared Stripe account: if the existing `/stripe-webhook` (shop payments) listens to `payment_intent.succeeded`, subscription invoices also reach it and its WhatsApp confirmation fails and is logged. Harmless noise; a separate Stripe account avoids it.
